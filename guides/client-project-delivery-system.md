# Client project delivery system

## Purpose

This guide defines a reusable way to run client-facing projects so work is clear before build, stable at launch, and easy to hand off afterward.

## What this system covers

- project intake and discovery
- scope alignment and approvals
- content and asset collection
- launch readiness
- client handoff and training
- maintenance and support workflow

## Core principle

A client project is not complete when the code works. It is complete when:

- the scope is clear
- approvals are traceable
- the launch path is safe
- the client can operate what was delivered
- the next support step is obvious

## Suggested lifecycle

### 1. Intake
Capture:
- project goal
- audience
- required pages or workflows
- budget and timing constraints
- integrations
- approval contacts

### 2. Scope alignment
Define:
- what is included
- what is explicitly not included
- what the client must provide
- what counts as a revision vs a new request

### 3. Build preparation
Gather:
- content
- assets
- branding
- domains and hosting access
- analytics and form requirements

### 4. Implementation
Build against the agreed scope and maintain a visible list of assumptions, blockers, and pending approvals.

### 5. Launch readiness
Verify:
- pages
- links
- forms
- metadata
- responsiveness
- analytics
- error handling
- deployment settings

### 6. Handoff
Deliver:
- credentials and access map, if applicable
- editing instructions
- deployment notes
- support boundaries
- known follow-up items

### 7. Maintenance
Define:
- what support includes
- what response expectations exist
- how changes are requested
- what incidents or regressions should be logged

## Guardrails

- never assume client-provided content is final until confirmed
- separate revisions from net-new scope clearly
- track pending approvals in writing
- do not launch without a checklist
- handoff must be usable by someone who was not in the build session
